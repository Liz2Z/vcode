# 减少 TypeScript 服务内存应考虑原生实现

## 问题与纠正后的预期

用户指出 Node LSP 内存较高，代理最初只讨论关闭文档和限制堆内存；用户澄清希望替换为非 JavaScript 实现。应先评估成熟原生实现，不能把优化范围局限于现有 Node 链路。

## 原因

已核实旧实现通过 Node 启动 typescript-language-server，再启动基于 JavaScript 的 tsserver。协议桥接与类型分析各占一个进程。大型项目类型图造成的具体内存构成未做堆分析，不能仅凭截图断定为泄漏。

## 修正措施

采用微软 TypeScript 7.0.2 的平台原生可执行文件，Swift 客户端直接通过 stdio LSP 连接；移除 Node 桥接、旧 tsserver 参数与应用内 Node 运行时。打包时保留原生二进制相邻的标准库声明和许可证；开发、CI 与发行构建使用同一锁定版本。现有悬停、定义、引用和语义高亮继续使用标准 LSP 映射。

## 防止再犯

- 先核实当前官方正式版本与运行时依赖，不把 npm 分发等同于必须在 Node 中运行。
- 对同一项目、同一文件和同一查询序列比较进程树 RSS，不把 RSS 与资源窗口的 memory footprint 混为同一指标。
- 保留语义引用、遮蔽作用域、多层跳转、文档更新及失败恢复回归，不只测试服务能够启动。
- 应用包必须携带标准库声明，发行应用不能悄悄回退到本机 Node 或源码目录。
- 本次修改范围是语言服务与相关构建、测试和文档，不覆盖同时进行的 diff 改造。

## 验证状态

原生服务独立协议探测已返回悬停、定义、引用与文件内高亮；同项目初步 RSS 对照约 909 MB → 416 MB。完整回归及实窗验证尚待完成，不能提前记为通过。

## 引用语义兼容与复验

首次原生回归有两个原数量断言失败：原生服务在 includeDeclaration:false 时连 import 别名也排除，导致使用列表少一项。采用 includeDeclaration:true 获取语义位置，再用真实 definition 结果移除目标声明，保留 import 使用；不靠名称或文本匹配，也未放宽已有数量断言。

35 项相关测试、release 构建、ZIP / DMG 和签名检查通过；实窗确认 Ready 与单个原生子进程。窗口操作受到其他操作干扰，类型悬停、使用处 ⌘点击跳转和定义处 ⌘点击引用列表为需要用户验证；具体请求已发送，当前未收到结果。完整结果见 docs/verification/2026-10-26-native-typescript.md。UI 阶段没有修改产品或测试代码，本次相关 12 项冻结指纹保持一致。

## 预览应用的辨认方式

用户反馈找不到“VCode Native Preview”菜单名称。此前只提供前台应用的菜单名称，却没有区分菜单名与窗口标题：窗口仍按项目显示为 primary — VCode，应用在后台时用户也看不到该菜单名。这是说明不清楚，不能将“启动成功”当成用户已经找到预览。

修正措施：按预览独立 bundle ID 定位并抬高窗口，实际打开 VCode Native Preview 菜单核对；提供预览应用的完整路径，明确菜单名称位于 macOS 顶部，而不是窗口标题或功能入口。后续请求用户验证前，应核对前台窗口并同时提供可复现的应用位置。用户本次只反馈没有找到预览，三项语言交互仍然未验证，不能记为通过。


用户再次指出同时打开三个 VCode，仍无法辨认目标。仅提供菜单名和路径并未解决辨认问题。修正为把本次临时示例项目命名为“Go 原生服务测试”，在按独立 bundle ID 选定的预览中打开该目录和 main.ts，实际核对窗口标题、左上角项目名及 TypeScript Ready。没有关闭其他实例，也没有改用户项目。以后并行预览必须给出窗口内直接可见且唯一的名称；“已切前台”不能替代清晰的视觉标识。三项语言交互仍等用户反馈。


## 测试版需要独立图标

用户要求测试版采用已有光剑图标，进一步纠正三个同图标实例难以辨认的问题。已有素材足够，复用写实 v2 的 ICNS，不重新绘制或生成。构建脚本按 preview / release 选择图标，默认本地测试和 GitHub 预览用光剑，正式构建用灰白折纸。检查点：验证最终应用资源和重开后真实图标，不只修改素材或口头起名；菜单名、窗口项目名与图标是三个不同的辨认线索。

用户在明确显示“Go 原生服务测试”项目的窗口中反馈“没毛病，推送”，三项语言交互现记录为用户实测通过，不能写成代理自动化或鼠标验收。图标为此后新增要求，另行验证。


## Dock 图标占位过满

用户提供实际 Dock 截图，指出光剑图标占得太满。预期缩小整个圆角底板与光剑，增加透明安全边距，不只收小剑刃。此前只核对 ICNS 与源素材一致，未核对最终 Dock 占位，不能据此判断留白自然。通过内置 imagegen 基于原写实 v2 增加约 13% 的四周透明边距，保存独立留白版 PNG / 多尺寸 ICNS，preview 构建引用新文件；旧素材保留。原因目前只确认视觉占位偏满，没有把系统图标缓存或缩放算法写成根因。检查点：查看实际 Dock / Finder 小尺寸并与相邻图标比较，不能只看大图或 ICNS 能否解码。实窗复验待完成。


最终用户反馈“现在合适”，留白修正版在 Dock / ⌘Tab 中的尺寸现记录为用户实测通过。Finder 由代理实窗核对；二者证据来源分开记录。
