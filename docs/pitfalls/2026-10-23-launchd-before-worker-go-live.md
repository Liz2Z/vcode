# 系统级 PM2 托管应在初始化阶段完成

## 问题

在已验证 idev007 重启后系统级 PM2 网络正常后，建议将托管启用与重启放到后续上线阶段。用户纠正：初始化时直接完成系统配置和重启验收，上线后无需再为托管重复重启。

## 纠正后的预期

初始化时配置并启用系统级 launchd，用空业务清单运行 PM2，在所有配置完成后统一重启并验收。Worker、Monitor 留待上线时启动并保存清单，复用已有 PM2 托管。

## 原因

把“不启动 Worker、Monitor”扩大为“不运行 PM2、不启用系统级托管”，混淆了基础运行环境与业务上线，导致重启验收被后移并重复安排。

## 修正措施

已修订 Downloads SOP、插件参考副本和 Skill 入口：将前面的重启检查合并到初始化末尾，以空业务清单配置系统级 PM2，验收未登录桌面的 SSH 和断开 SSH 后后台网络访问。插件参考副本与源 SOP 保持逐字节一致。

## 防止再犯的检查点

- 分别定义 PM2 基础托管和 Worker、Monitor 业务进程的状态，避免把禁止启动业务服务理解成禁止配置基础托管。
- 全新节点使用空业务清单；已有进程和 dump 必须先核对，不直接清空或覆盖。
- 只检查 SSH 网络不足以证明后台网络可用，探针应在系统级 PM2 下运行，并跨 SSH 断连观察。
- 初始化配置与重启验收放在同一流程，后续上线不重复执行托管迁移。
- 新的空业务清单和探针流程已完成文档及 PM2 源码行为核对，尚未完成另一台全新机器上的端到端实机验证。
