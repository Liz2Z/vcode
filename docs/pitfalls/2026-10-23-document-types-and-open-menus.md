# 区分系统文档类型注册与第三方打开菜单

## 问题与纠正后的预期

用户询问如何出现在打开列表时，直接给出 Codex 自定义 handler 配置，没有先交代 macOS 自身的文档类型注册。用户指出应用可以声明自己能打开的文件类型，并明确要求 VCode 声明常见开发文件。

## 原因

将特定应用的菜单配置与操作系统的文件处理能力混在了一起。VCode 的 Info.plist 原先没有文档类型声明，且外部打开入口把所有路径当成项目文件夹；仅配置菜单标签不能补齐文件打开能力。截图所在菜单是否枚举 Launch Services 不能只凭外观判断；此前对其固定识别机制的说法未通过本地实现完整核实，应保留这一限制。

## 修正措施

通过 macOS 原生文档类型声明，注册常见源码、脚本、配置、文本及项目文件夹，以 Viewer／Alternate 提供查看，不设置为默认应用。扩展名声明参考已安装 VS Code 的注册方式，并补充通用文本类型。外部事件与启动参数统一进入文件／目录解析：外部文件统一复用 Git domain 识别仓库和 worktree 根目录，同一根目录复用活动栏，仓库外文件明确拒绝；批量请求排队，不把文件误当目录。注册、外部事件及实际窗口验证结果完成后另行补录。

## 防止再犯的检查点

- 先确认是 Finder 的系统菜单，还是应用自行构建的菜单；不知道时明确未核实。
- 系统注册使用原生文档类型声明及 Launch Services，不以第三方专用配置替代通用能力。
- 文档类型声明、能否接收打开事件、能否真正显示内容分开验证；冷启动、运行中和多个带特殊字符的路径都要覆盖。
- 只读应用使用 Viewer／Alternate，不抢占默认关联，不以通配符承诺任意二进制文件可读。
- 系统菜单与第三方菜单分别报告；未验证的集成不能宣称可用。UI 验收阶段不修改产品或测试代码。

## 外部文件只接受 Git 仓库

用户进一步收窄范围：外部打开的文件必须位于 Git 仓库内。此前增加了普通文件回退到父目录的策略，超出这次需要。删除该回退及“当前目录包含即接收”的旁路；文件统一通过 Git domain 查找工作树根目录，无仓库明确拒绝，不切换当前会话。普通文件夹仍沿用项目浏览入口。检查点：覆盖主仓库、linked worktree、仓库外文件拒绝、拒绝后仍能接收有效文件，避免将普通文件夹浏览与外部单文件接收混为一条规则。验证待补录。

验证补录：最终 18 项相关测试、发行构建及 12 类系统处理器查询通过，Finder 菜单已列出 VCode；系统冷启动／运行中批量文件事件、Git 与 linked worktree 定位、真正仓库外拒绝及双栏保留已实窗验证。物理 Dock 拖入仍需用户验证；默认关联在强制注册前后查询一致，但后续实时时界面变化与实际 VCode 启动后部分类型默认目标变化，原因未核实，不把未主动设置默认等同于最终默认始终不变。117 项固定指纹一致，验收中未修改产品或测试代码。

## 拒绝文件必须有可感知的反馈

用户实测仓库外文件“毫无反应，至少给个反应”。旧实现仅把错误写入底部状态栏，反馈位置不显眼，而且后续状态刷新或批量成功项可能覆盖；此前只验证状态文字存在，不能据此认定用户能感知拒绝。用户当前现场是否还受到旧进程或刷新影响未核实。

纠正后的预期：冷启动与运行中拒绝文件都展示原生提示框，明确文件路径及 Git 仓库限制／实际错误，确认后继续阅读；一批错误合并提示，保留有效项与原会话，不堆叠弹框。已有系统对话框时等待可展示后提示。修正措施为使用 AppKit 的 NSAlert sheet 汇总外部打开错误，状态栏仅作补充。自动化与实窗验证完成后分别补录。

检查点：不能把“错误字符串写入控件”当成“用户有明显反馈”；覆盖空窗口、已有双栏、混合有效／无效文件、重复失败路径、关闭提示后继续打开、既有对话框的等待以及手动切换／退出时取消旧提示。UI 验收固定后只测试和记录，不改代码。

## 用户否定原生警告弹框

原生错误 sheet 完成首轮自动化、冷启动实窗显示后，用户明确反馈“原生弹框太丑了”。这是本轮新的视觉纠正，原生弹框方案停止验收并撤回，不将该版本的通过结果用作新版验收结论。

纠正后的预期是应用自身灰色／暖黄色样式的非模态提示条：固定在工具栏下方，不遮罩、不抢走输入焦点，显式展示文件名、原因与路径，错误持续保留到用户关闭；批量错误合并，同类原因去重，长路径自然截断，完整信息可悬停查看。关闭按钮沿用共享反馈组件，当前项目、分栏和阅读可继续使用。与已经被用户认可的原生 Git 选择器无关，不借机改造其他浮层。

原因是把“原生方案优先”机械套用到需要融入应用视觉的日常反馈，忽略了整体现有灰度设计；用户此前要求“至少给个反应”，并没有要求系统警告对话框。修正为工作区内提示条，并修订相关 UI 预期及回归；新版验证待补录。检查点：错误必须明显，同时避免模态打断；不能以错误可见为由忽略用户明确的视觉选择。

## 错误反馈放在中心，不能改变阅读布局

用户进一步纠正：提示应在中心区域替换空白欢迎提示，或使用自定义弹框；顶部提示条影响布局，反而更丑。此前自行将“应用内提示”具体化为占位条，加入高度及间距约束，导致侧栏和代码区域下移、可视高度缩小。原生弹框与顶部条方案均已被用户否定，不应再次带回。

按此次明确反馈改为代码区中央的自定义浮层：复用既有 FloatingSurface 灰底、暖黄色、圆角及投影，覆盖显示，不参与原分栏布局；空状态隐藏原欢迎内容，已有文件保留其标签、位置与分栏。支持关闭／确认／Escape，并恢复焦点；浮层上的点击不能激活下方另一个编辑器。修订布局回归，直接比较错误出现前后的编辑区及侧栏几何，同时校验窄宽往返的居中和边界。此次是用户明确的新修正指令，先前提示条验收停止；新版结果另行记录，不沿用旧版本通过结论。

最终居中浮层验证：18 项相关测试及发行构建通过；冷启动中心反馈、空欢迎区域覆盖、Escape／Close、批量失败与有效项混合、关闭后双栏和活动文件保留已实窗确认。实际应用已重开到原工作区。118 项固定指纹一致，未在该阶段修改代码；不沿用已被用户否定的原生弹框或顶部条结论。
