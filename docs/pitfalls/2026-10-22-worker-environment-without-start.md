# Worker 环境初始化不包含服务启动

## 问题

环境初始化清单将安装、配置开机启动和启动 Worker、Monitor 合并，用户明确纠正：Worker 和 Monitor 不得启动，启动服务不属于本次环境配置。

## 纠正后的预期

准备运行时、工具、仓库、依赖、CLI、Skills 和节点配置，初始化期间不启动 Worker、Monitor。2026-10-23 用户进一步明确：系统级 PM2 托管应在初始化时配置完成，并在初始化末尾完成重启验收；之后上线无需再为建立托管重复重启。PM2 基础托管与 Worker、Monitor 业务进程的启动需要分别处理。

## 原因

清单沿用了运行部署的验收方式，将注册和持续心跳当作初始化验收，混淆了环境准备与服务上线的边界。

## 修正措施

最初通过生成禁用的启动文件避免业务进程误启动。后续调整为初始化时配置并启用系统级 launchd，以空业务清单托管 PM2，统一在配置末尾重启；验收未登录桌面的 SSH、PM2 托管关系及断开 SSH 后的后台网络访问。Worker、Monitor 仍保持无进程、无监听、未向 Core 注册，实际业务上线另行确认。

## 防止再犯的检查点

- 初始化不启动 Worker、Monitor，不复用含有业务进程的 PM2 dump。允许系统级 launchd 启动空业务清单的 PM2 及日志轮转组件。
- 检查安装脚本和 package lifecycle 是否包含服务启动副作用。
- 系统级 launchd 托管配置及重启验收在初始化阶段完成，不从 SSH 另起 PM2 daemon，不把本应前置的托管工作推到上线后。
- 不复制其他机器的 PM2 dump、会话、认证缓存或私钥。
- 已在 idev007 验证系统级 launchd 托管业务进程时，重启后未登录桌面的有线 SSH 自动恢复，断开启动 SSH 后两分钟内心跳持续。修订后的“全新空业务清单 + 临时网络探针”初始化流程尚未在另一台新机器上完整执行；不能把该流程写成已完成实机验收。
