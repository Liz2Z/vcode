# 筛选后的文件行无法点击切换

## 问题与预期

实窗验收时，在 Files 中筛选 request.ts 后，点击 auth/request.ts 或 uic-request.ts 无法选中并切换源码。源码标签切换可以工作，因此不能将标签切换通过当作文件树点击通过。

用户确认真实操作也无法切换；调整侧栏大小、切到 Changes 再切回 Files 后恢复。这是用户验证的应用问题，不能继续归为工具限制。

预期：筛选完成后，任何匹配文件行都可以直接选中和阅读，无须先调整侧栏或切换模式。

## 当前证据与原因

已有实窗截图、辅助功能状态和用户确认；触发及恢复步骤已记录。具体根因尚未核实，不把布局／命中区域等排查方向写成已确认原因。

## 后续措施与检查点

- 本轮 UI 验收未通过，等待用户另行明确要求修复；不在 UI 验收中修改产品或测试代码。
- 获得修复授权后，先补充可重现筛选、首次点击和模式往返的回归，再修正已核实原因。
- 后续验收需覆盖筛选后直接点击不同文件、点击已打开文件、清空筛选、刷新及侧栏宽度变化，不能依赖布局变化让问题自行恢复。
- 区分代理实窗验证与用户验证；保留原始失败，不将缩放后的恢复记为原操作通过。

## 用户授权修复后的诊断与实现

用户通过批注明确要求修复后才修改实现。独立诊断构建在真实 zan-cli 复现：筛选 request.ts → 在 Changes 打开 qima-login/request.ts 删除 diff → 返回 Files → 点击 auth/request.ts。NSWindow 及 FileOutlineView 日志均记录正确的行号与鼠标按下，但原生文件行的 super.mouseDown 返回后没有选择，鼠标抬起也未触发文件 action；单独构造的树和初次点击可以正常工作。原生控件内部为何跳过该选择尚未核实，不将窗口拖动或命中区域猜测认定为根因。

项目原本把目录点击交给自己处理，文件点击则依赖原生跟踪循环和缓存的 clickedRow。现在统一为按下选中、抬起激活：明确按当前数据中的行选择，抬起时验证仍是同一节点，再通过原生 sendAction 打开一次文件。拖出行取消打开；reloadData 清除旧按下及 hover 状态，避免刷新后错误激活替换行。键盘选择仍使用原有原生选择回调，不改文件树的数据和筛选规则。

新增回归覆盖筛选事件、Files／Changes 往返、重复点击已打开文件、暂存分类、拖出取消及按下后筛选替换节点。最终固定构建实窗复验结果待补充。

## 固定构建复验结果

106 项自动化测试全部通过。最终 release 构建在真实 zan-cli 中通过此前失败的完整操作：筛选 request.ts，打开删除文件 diff，返回 Files 后不缩放侧栏直接打开 auth/request.ts，再切换 uic-request.ts、xiaolv/request.ts 及已打开文件；重复点击、刷新、清空并重新筛选均可直接打开。侧栏由 240 收窄至 208 后也能切换。目录文字、右侧空白与箭头各自只切换一次，关闭标签正确生效。

验收前后 81 个源码／测试文件指纹一致；发行包签名有效，二进制 UUID 与 release 一致。实窗结果、截图和 AX 状态保存在 `.build/diagnostics/filter-click/`。本轮只复验相关场景，不冒充全产品 UI 验收。
